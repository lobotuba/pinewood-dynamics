GRAVITY RACER
GUI / UX MOCKUP - STANDALONE RACE-SOFTWARE VISUAL DIRECTION
Revision intent: Gravity Racer remains completely independent software. GrandPrix Race Manager is only a loose visual-context reference for a familiar derby/race-night desktop-software feel. No compatibility, shared files, workflow integration, branding relationship, or common functionality is implied.

1. PRODUCT UI POSITION
Gravity Racer should feel immediately at home on a computer used around a gravity-racing event while retaining its own name, branding, information architecture, file format, simulation engine, and design workflow.

The application must NOT present itself as a module, extension, companion utility, or product from the maker of GrandPrix Race Manager.

2. CORE WORKFLOW
Preserve the Gravity Racer workflow:
DESIGN -> COMPONENTS -> WHEELS -> OPTIMIZE -> RACE SETUP -> RACE -> ANALYZE -> BUILD

Do not restructure Gravity Racer around another application's race-management workflow.

3. VISUAL DIRECTION
Desired character:
- Standalone desktop engineering/racing application.
- Purposeful race-night utility feel rather than generic web dashboard.
- Information rich without becoming visually noisy.
- Strong grouping of controls into clearly labeled panels.
- Obvious distinction among configuration, live race, analysis, and build activities.
- Large, accessible primary actions suitable for parent/child use.
- Precise engineering controls available without dominating Kid Mode.

Do not directly copy proprietary logos, branded artwork, screenshots, exact icons, or other protected visual assets from third-party software.

6. COLOR / VISUAL SEMANTICS
Use an original Gravity Racer palette, but use conventional race-operations semantics:
- Neutral application chrome/background.
- Strong blue or another distinctive Gravity Racer primary color for selection and primary commands.
- Green for verified/pass/ready states.
- Amber for warning/estimated/uncharacterized states.
- Red for illegal/fail/contact/error conditions.
- Lane colors used consistently when multiple cars are shown.

Exact palette values are a Gravity Racer design choice and are not claimed to be values from any third-party race software.

7. TYPOGRAPHY
Use a highly readable system/UI sans-serif with compact engineering labels and larger race/timing numerals. Prefer standard desktop readability over stylized game typography.

Suggested Gravity Racer convention:
- Application/menu: normal UI size.
- Panel heading: bold, compact.
- Data labels: compact UI size.
- Primary numerical result: substantially larger.
- Race timer: largest numeric element during a race.

Exact third-party fonts are not assumed.

24. KID MODE
Kid Mode retains the same shell but simplifies controls:
DESIGN -> ADD STUFF -> WHEELS -> MAKE IT FASTER -> RACE -> WHY? -> BUILD

Use larger labels and hide detailed coefficient editors. The underlying project and physics remain the same.

25. BUILDER MODE
Builder Mode uses the full normal Gravity Racer workflow and emphasizes physical values, dimensions, material, mass, CG, rules compliance, wheel setup, and build exports.

26. ENGINEERING MODE
Engineering Lab exposes parameter provenance, solver settings, energy residual, detailed telemetry, parameter sweeps, and uncertainty controls.

27. VISUAL CROSSOVER BOUNDARIES
Allowed design inspiration:
- Compact desktop application chrome.
- Familiar race-control seriousness during Race mode.
- Bounded functional panels.
- Prominent timers/results.
- Clear settings/status separation.
- Information-dense but readable layouts.

Do not imply:
- Data compatibility.
- Shared racer databases.
- Race-file compatibility.
- Timer integration with another product.
- Shared vendor or endorsement.
- RaceFX/RaceReplay/DerbyDMV/DerbyMobile integration.
- Identical menus/workflows.

Do not copy:
- Logos.
- Proprietary artwork.
- Exact icon assets.
- Product name treatment.
- Screenshots as UI backgrounds.

28. DESIGN SYSTEM GOAL
The desired visual relationship is:
"This clearly belongs in the world of gravity-race software."

The undesired relationship is:
"This looks like a screen or module from GrandPrix Race Manager."

29. CORE IDENTITY
Gravity Racer's strongest visual feature remains the interactive physical car in Orbit View. The race-software crossover should frame this experience, not suppress it.

Final principle:
A user familiar with derby race software should find Gravity Racer operationally comfortable, while a new user should see a distinct, modern, standalone product whose central purpose is designing, simulating, optimizing, and building a real gravity racer.

30. CONSTRAINT-AWARE STANDALONE UI
Add a persistent group without changing the standalone product identity:

[LOCK] Wheelbase             LOCAL/FROZEN

31. DATUM OVERLAYS
View Options shall add Axle Datums, Wheelbase Dimension, Gate Contact Zone, Wheel Swept Envelopes, Axle Structural Zones, and Guide-Rail Clearance.

32. INSPECTION PROVENANCE
Every line shall expose RULE, LOCAL LOCK, MEASURED, DERIVED, ESTIMATED, UNKNOWN, or ADVISORY status. The unchanged-wheelbase requirement shall not be presented as if explicitly stated by the current published rule page.

33. AI CONSTRAINT SUMMARY
Before generation, show that the design will preserve published dimensional and gate rules, locked axle datums and wheelbase, protected wheel/clearance envelopes, and selected manufacturing difficulty.

34. READINESS
Engineering Test may simulate a deliberately noncompliant design if clearly labeled. Certified ruleset racing and Build export require all published hard rules and active local locks to pass.
